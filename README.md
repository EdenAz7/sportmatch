# SportMatch ⚽

פלטפורמה שמחברת בין חובבי ספורט לארגון אירועים, עם התאמה חכמה ובטיחות.
פרויקט בקורס **ניתוח ותכנון מערכות מידע א'**. מגישים: עדן אזולאי, לביא וילנר, דוד בראל, תומר סעד.

**האפליקציה:** https://edenaz7.github.io/sportmatch/

## ארכיטקטורה (Client–Server)

| שכבה | טכנולוגיה |
|---|---|
| לקוח | React 19 + TypeScript + Vite, Tailwind, PWA (עברית, RTL), אחסון ב-GitHub Pages |
| שרת ובסיס נתונים | Supabase: PostgreSQL (מודל רלציוני), Auth, Row Level Security, פונקציות RPC ב-PL/pgSQL, pg_cron |
| מפות | OpenStreetMap + Leaflet, Nominatim לחיפוש כתובות |
| תשלום | קישור Bit שהמארגן מצרף לאירוע; המארגן מסמן מי שילם |
| אנליטיקה | Google Analytics 4 (`VITE_GA_ID`) + טבלת `app_events` פנימית ולוח ניהול |

## הרכיב האלגוריתמי

### 1. מנוע ההתאמה (Match Engine)
`supabase/migrations/0002_match_engine.sql`

לכל זוג (משתמש, אירוע):

```
Score = w1·Sport + w2·Level + w3·Distance + w4·Time + w5·Rating + w6·History
P(join) = σ(b + Score)   ← מוצג כ"אחוז התאמה"
```

| מדד | חישוב (0..1) |
|---|---|
| Sport | 1 אם הענף בפרופיל |
| Level | `1 − |רמת משתמש − רמת אירוע| / 4` |
| Distance | `exp(−km / 7)` (Haversine) |
| Time | התאמה לחלונות הזמן המועדפים (אמצע שבוע/סופ"ש × בוקר/צהריים/ערב) |
| Rating | מוניטין ממוצע של המשתתפים (ספורטיביות × אמינות הגעה) |
| History | שיחק בעבר עם המשתתפים / המארגן |

סינון קשיח: אירוע פתוח, עתידי, לא מלא, בטווח המרחק של המשתמש.

**הערכת רמה בייסיאנית:** `(3·self + Σ דירוגי עמיתים) / (3 + n)`.

**כיול משקלים (`calibrate_weights`):** כל המלצה שמוצגת נשמרת ב-`recommendation_log` עם המדדים, ומסומנת `joined` כשהמשתמש מצטרף.
הכיול מריץ רגרסיה לוגיסטית עם Projected Gradient Descent ורגולריזציית L2. המשקלים נשארים אי-שליליים כדי שאפשר יהיה לפרש אותם.
הוא מדווח Log-loss, AUC ודיוק למשקלים הישנים ולחדשים על אותם נתונים.

*אימות על נתונים סינתטיים* (2,000 המלצות שנוצרו ממודל עם משקלים ידועים):
משקלים אמיתיים `b=-3, S=2.5, L=3.0, D=2.0, T=0.3, R=0, H=2.0` → משקלים שהכיול מצא `b=-2.86, S=2.37, L=2.74, D=1.83, T=0.45, R=0.15, H=1.93`.
Log-loss ירד מ-0.673 ל-0.414.

### 2. חלוקה לקבוצות מאוזנות (Team Balancer)
`src/engine/teams.ts`. זו בעיית חלוקת מספרים (Number Partitioning, NP-קשה):
- 2 קבוצות ועד 20 שחקנים: חיפוש מלא שמוצא את החלוקה האופטימלית.
- אחרת: אלגוריתם חמדני (השחקן החזק → הקבוצה החלשה) + חיפוש מקומי בהחלפות זוגות.
- קו בסיס להשוואה: תוחלת הפער בחלוקה אקראית (Monte-Carlo).

בבדיקות (100 משחקים אקראיים של 10 שחקנים) החלוקה המאוזנת קרובה פי 10 לפחות מחלוקה אקראית.

## מדדי ביצוע (לפני/אחרי)
לוח הניהול (`/admin`, פונקציה `admin_stats`) מציג: משתמשים פעילים, אירועים בשבוע, אחוז אירועים שהתמלאו, זמן עד מילוי,
המרת המלצות, הצטרפות דרך המלצה מול חיפוש, חזרה תוך 30 יום, ופער בין קבוצות מול חלוקה אקראית.

## הרשאות
משתמש · בעל מתקן · מנהל מערכת (כיול משקלים) · מבקר מערכת (צפייה בלבד).
כל הכתיבה לטבלאות הרגישות עוברת דרך פונקציות שרת שבודקות הרשאות, ו-RLS מופעל על כל הטבלאות.
